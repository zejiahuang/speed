# Steamcommunity_302 转发机制研究 —— 与 watt 的对照

> 对 `D:\3\Steamcommunity_302\转发机制与IP来源.md` 的独立复核，加上本机实测。
> 结论只写我亲手验证过的部分；未验证的推断会明确标注。

---

## 1. 它和 watt 是**两种相反的架构**

| | Steamcommunity_302 | watt |
|---|---|---|
| 加密流量 | **本地终结**（自签 CA 装进系统根，Caddy 解密） | **不碰**（原样转发加密字节） |
| 改 Host / SNI | 能改 | 不能改 |
| 拿 IP 的手段 | 规则里写死上游 + 运行时优选 | 规则里写死地址 |
| 权限 | 管理员（改 hosts、装根证书、WinDivert 内核驱动） | 免 Root |
| 失败时能做什么 | 换上游、换 SNI、改 Host、改 UA | **只能换一个 IP** |

一句话：**S302 的「救援」能力来自解密，watt 的救援能力只能来自「换地址」。** 这决定了下面哪些能借鉴、哪些不能。

## 2. 已实测确认的机制

### 2.1 三层名字分离（Akamai 路径）—— 最核心的手法

S302 把**一个请求拆成三个不同的名字**，分给三个不同的层：

| 层 | 名字 | 作用 |
|---|---|---|
| 拨号名 | `steamstore-a.akamaihd.net.edgesuite.net` | DNS 解析出**能连通的**边缘 IP |
| SNI | `officecdn-microsoft-com.akamaized.net` | 决定边缘出示哪张证书 |
| Host 头 | `store.steampowered.com` | 决定 Akamai 路由到哪个源站 |

实测（本机，直连）：

```text
拨号 steamstore-a.akamaihd.net.edgesuite.net:443
  SNI  officecdn-microsoft-com.akamaized.net
  Host store.steampowered.com
→ HTTP/1.1 200 OK
→ Set-Cookie: steamCountry=CN|54337fe19557206c3d9c898122ecb3bc
```

真实 Steam 商店页面被取回。**三个名字缺一不可**，因为边缘证书的 SAN 是：

```text
DNS:a248.e.akamai.net, DNS:*.akamaized.net, DNS:*.akamaihd.net
```

对它做逐个名字匹配：

| 名字 | 结果 |
|---|---|
| `officecdn-microsoft-com.akamaized.net` | **匹配** |
| `store.steampowered.com` | 不匹配 |
| `steamstore-a.akamaihd.net.edgesuite.net` | 不匹配 |

**这就是 `tls_server_name` 必须写成一个「无关」域名的原因**：真实域名和拨号名都不在证书覆盖范围内，只有一个 Akamai 自家域名能通过验签。它不是随手写的，是整条链路的承重点。

> **对 watt 的意义**：watt 不解密，所以**改不了 SNI**。客户端自己的 ClientHello 里写死了原域名。
> 这意味着 S302 这条最有力的救援手段，watt **结构上无法采用** —— 不是实现问题，是设计取舍的代价。

### 2.2 `edgesuite.net` 是选路标签，不是另一台服务器

同一个源站，加不加后缀解析到**不同的边缘 IP**：

```text
steamstore-a.akamaihd.net                 -> 23.33.126.169
steamstore-a.akamaihd.net.edgesuite.net   -> 23.220.71.183
```

证书是同一个 Akamai 泛域名证书。所以「加后缀」本质是**向 Akamai 要一个不同（且在国内可达）的边缘节点**，不是换了服务商。

### 2.3 Cloudflare 优选路径当前是**坏的**（诚实记录）

文档描述「优选 IP 写进 hosts 直连」。实际系统 hosts 里确实有 4 条：

```text
172.67.64.100   discord.com.cdn.cloudflare.net          #S302
172.67.160.100  nexusmods.com.cdn.cloudflare.net        #S302
104.17.160.100  deepl.com.cdn.cloudflare.net            #S302
104.17.96.100   www.steamgriddb.com.cdn.cloudflare.net  #S302
```

手法是造一个**合成主机名** `<真实域名>.cdn.cloudflare.net`，指望 Cloudflare 用 `*.cdn.cloudflare.net` 的证书接住它。实测（对优选出的 IP 逐个试 SNI）：

| SNI | 结果 |
|---|---|
| `discord.com.cdn.cloudflare.net` | **握手被拒**（SSL alert 40） |
| `discord.com` | 握手被拒 |
| `cloudflare.com` | OK（出示 GTS Root R4） |

IP 本身 TCP 443 可达、也能服务 `cloudflare.com`，但**不接这两个名字**。所以这条优选路径在本次配置下不工作。
旁证：Caddyfile 里紧挨着的一行被注释掉了 —— `#reverse_proxy https://parsec.app.cdn.cloudflare.net`，说明这类名字是会失效、需要人工增删的。

**这与 watt 已有的 Discord 结论一致**：Discord 两端都失败，不是内核写错了。

### 2.4 上游目标就是一份「写死 IP 的规则文件」

从生成的 Caddyfile 提取全部上游：**861 个不同主机名，其中 150 个是裸 IP**。

`github.com` 这一段：

```caddyfile
reverse_proxy https://20.200.245.247 https://20.205.243.166 https://20.207.73.82 \
              https://20.27.177.113 https://20.233.83.145 {
    lb_policy random_choose 3
    max_fails 3
    fail_duration 3s
    unhealthy_latency 500ms
    header_up Host {host}
    transport http { tls; tls_server_name "Github" }
}
```

**5 个 IP + 随机选 3 + 失败熔断。** 这和 watt 的 `Router` + `IpSelector` + `report_success`/`report_failure` 是同一个设计意图。

## 3. 对 watt 最有价值的一条发现

> **本节结论已经被实测推翻（2026-09-26，见 §3.0）。** 原文保留在下面作为当时
> 的推理记录，因为「归因错了」这件事本身值得留档。**不要再用原文的数字下结论。**

### 3.0 修正：密度不是瓶颈，正确性才是

本节原文据以立论的密度数字是对**旧规则源**测的，今天对同一端点
`https://abhuang.dpdns.org/1` 重测（hosts 文本，跳过 `#` 注释与环回地址）：

```text
域名总数   = 5225      （原文 2879）
地址总数   = 15952     （原文 2966）
平均       = 3.05 个 IP/域名   （原文 1.03）
多 IP 域名 = 5225 个（100%）   （原文 79 个，2.7%）
```

分布：3 个地址 → 5102 个域名；2 个 → 23；6 个 → 89；5 个 → 9；9 个 → 1；12 个 → 1。
**没有任何域名只有一个地址。** 因此本节的核心论断——「规则源只给一个地址，
选择器没有可选项」——**现在不成立**：选择器有真实排序空间。

重测方法（可复现）：拉 `/1`，跳过 `#` 行与环回行，按最后一个字段聚合域名、统计
行数，与上表核对。

**新的瓶颈是地址正确性，不是地址数量。** 对该端点抽测 25 个域名，对每条规则
地址分别做 TCP 可达性 + TLS 证书校验（`server_hostname` = 该域名），结果
**约 7 成可用**（team-lead 测得 18/25 = 72%；独立复核另抽 25 个得 17/25 = 68%；
比例随样本与时刻波动，量级稳定在七成上下）。失败必须分三类，不能混为一谈：

| 失败类型 | 含义 | 排序能否救 |
|---|---|---|
| 证书不匹配 | TCP 连得上，但证书链不覆盖该域名 | **不能**。要救只能改 SNI / 中间人，watt 明确不做；架构上无解 |
| 连接被拒 | refused / reset / EOF | 能——换下一个地址 |
| 超时 | 无响应 | 能——冷却后换下一个地址 |

结论重写：**瓶颈不再是地址数量（选择器现在有排序空间），而是地址正确性。**
抽测里约 3 成的域名**一个能用的地址都没有**；其中证书不匹配这一类在不 MITM
的前提下**架构上无法解决**，唯一出路是换一个正确的地址。所以「多 IP + 熔断」
依然值得做，但**它的收益上限被地址正确性卡住**，而不是被数量卡住。

### 3.1 原文（保留，已被上面推翻）

**上游 hosts 源的 IP 密度太低，这才是 `PROXY_FAILED` 的根因。**

```text
域名总数 = 2879
地址总数 = 2966
平均     = 1.03 个 IP/域名
多 IP 域名 = 79 个（2.7%）
```

对照实测：

| 来源 | `github.com` 的地址 | 实测结果 |
|---|---|---|
| 我们的 hosts 源 | `51.142.105.107`（1 个） | **不可达** |
| S302 规则 | 5 个 Azure IP | **4 个 TLS 可用** |

逐 IP 验证 S302 那 5 个（用原 SNI `github.com` 直连）：

```text
20.200.245.247   TLS OK
20.205.243.166   TLS OK
20.207.73.82     TLS OK
20.27.177.113    失败
20.233.83.145    TLS OK
```

**结论**：`github.com` 走内核失败，不是因为内核选错了地址，而是因为**当时规则
源只给了一个地址，而那个地址是死的**。

> 注（2026-09-26）：`/1` 现在给 `github.com` 三个地址，不再是单地址。上述归因
> 对**那次测量时的快照**成立，但不能推广成「规则源普遍只给一个地址」——那已
> 被 §3.0 推翻。

这修正了一个容易搞错的归因：
- 我此前加的「规则地址全失败后回退系统解析」是**必要的兜底**（避免一条过期规则把域名变成故障）；
- 但它治的是症状。**治本的方向要按 §3.0 重写**：不是「提高 IP 密度」（密度已经
  够了，3.05/域名、100% 多地址），而是**提高地址正确性**——选出证书覆盖原域名
  且可达的那个地址。证书不匹配类失败在不 MITM 时无解，只能靠换地址。

## 4. 可借鉴 / 不可借鉴

### 可以借鉴

| 项 | 说明 |
|---|---|
| **多 IP + 熔断** | 已在 `Router`/`IpSelector` 里有雏形；~~差距在**规则源只给 1 个地址**，选择器没有可选项~~ **（2026-09-26 修正）**：`/1` 实测 3.05 地址/域名、100% 多地址，选择器**有**可选项；差距已转为**地址正确性**（证书不匹配/拒绝/超时） |
| **`dynamic` 运行时重解析** | Caddy 的 `dynamic a <name> 443` 会定期重查 DNS。watt 的 hosts 源是启动时快照，长跑会过期 |
| **健康判据多维** | S302 同时看 `max_fails` / `fail_duration` / `unhealthy_latency` / `unhealthy_status`。watt 目前只有连得上/连不上 |
| **上游按路径分流** | `@steamstreoapp` 匹配 `/app/*`、`/agecheck/*` 走不同上游。watt 若做应用级分流可参考这个粒度 |

### 不能借鉴（或代价不可接受）

| 项 | 原因 |
|---|---|
| **改 SNI** | 需要解密；watt 明确不解密。这是最大的一条能力缺口 |
| **改 Host / UA** | 同上。且 S302 往 UA 里塞 `Googlebot` 绕过年龄验证，属于伪造客户端身份 |
| **自签 CA 装系统根** | 违背免 Root；且私钥在程序目录，泄露即可伪造任意网站证书 |
| **第三方中继** | `str001~004.steam302.xyz`、`*.cdn.queniuqe.com` —— 流量在中继处已是明文 |
| **WinDivert 内核驱动** | 需管理员，且只校验文件存在性与版本号 |

### 信任边界（S302 自身的风险，与我们无关但值得知道）

- 规则文件**可远端下发且无签名**，只比对 `Last_update` 时间戳 → 服务器被劫持即可把任意域名指向任意上游
- 有 MITM 能力 + 私钥落地 + 无签名校验，这三者叠加是最危险的组合
- 文档自称「无恶意特征」，我复核的范围内（日志、配置、生成的 Caddyfile）**没有发现与描述不符的行为**

## 5. 能不能像 S302 做到？—— 分三种能力，答案不同

### 5.1 改 SNI / Host / UA → **不能**

需要解密 TLS。这是 watt 明确放弃的能力，不是实现难度问题。

### 5.2 多 IP + 熔断 + 多维健康判据 → **能，而且骨架已有**

`Router` / `IpSelector` / `report_success` / `report_failure` 就是同一个设计意图。
~~**真正的差距在规则源只给 1.03 个地址**，选择器没有可选项。~~
**（2026-09-26 修正）** 选择器**有**可选项了：`/1` 实测 3.05 地址/域名、100%
多地址。所以与 S302 的差距不再是「有没有多个 IP 可选」，而是**给定这些地址
后，哪些真的能用**——抽测 25 个域名约 7 成可用，失败分证书不匹配 / 拒绝 / 超时
三类。多 IP + 熔断能做的是在**可达性**这一类上换地址；**证书不匹配**这一类它
救不了（见 §5.3 的「不做 MITM」约束）。

### 5.3 edgesuite 这类「选路标签」→ **有条件地能**

这是最需要说清的一条。判据只有一句话：

> **watt 能用的替代地址，必须满足「其证书覆盖客户端要发的原域名」。**

实测该边缘证书的 SAN 是 `*.akamaihd.net` / `*.akamaized.net`，逐个名字验证：

| 客户端会发的 SNI | 证书是否覆盖 | watt 能否用这个地址 |
|---|---|---|
| `steamstore-a.akamaihd.net` | **覆盖** | **能** |
| `steamcommunity-a.akamaihd.net` | **覆盖** | **能** |
| `steamvideo-a.akamaihd.net` | **覆盖** | **能** |
| `store.steampowered.com` | 不覆盖 | **不能** |

对第一种，我做了不改 SNI 的端到端验证（这正是 watt 的形态）：

```text
拨号 steamstore-a.akamaihd.net.edgesuite.net:443
  SNI  steamstore-a.akamaihd.net     ← 保持原域名，watt 不需要改
  Host steamstore-a.akamaihd.net
→ HTTP/1.1 403 Forbidden
→ Server: AkamaiGHost
```

TLS 握手完整成功、证书可信（403 是路径问题，不是握手问题）。
**所以对 `*.akamaihd.net` / `*.akamaized.net` 这一族域名，watt 可以照搬 edgesuite 选路。**

对 `store.steampowered.com` 则不行：客户端发的是这个名字，边缘给的是 `*.akamaihd.net` 证书，
对不上。S302 之所以能用，正是因为它把 SNI 换成了 `officecdn-microsoft-com.akamaized.net`。

### 5.4 救援能力的边界（精确表述）

- **S302 的救援集**：任何**可达**且**能返回目标内容**的边缘 —— 证书是谁的都无所谓。
- **watt 的救援集**：可达、**且证书覆盖原域名**的边缘。

后者是前者的**真子集**。差集就是「所有真实前端都被阻断、只剩证书不匹配的替代边缘可达」的情形 ——
`store.steampowered.com` 这类域名就落在差集里。

**结论：watt 做不到 S302 的全部，但能做到其中一大块，而且不需要 Root、不装根证书、不破坏端到端加密。**
对 `*.akamaihd.net` / `*.akamaized.net` / 任何「同一张泛域名证书覆盖」的域名族，edgesuite 式选路
可以直接用；对第三方域名（`store.steampowered.com`），只能寄望于真实前端里有可达的。

### 5.5 因此真正该做的事

按性价比排序：

1. ~~**提高规则 IP 密度**（当前 1.03/域名）。这是唯一能立刻扩大救援集的改动，
   而且 `github.com` 的实证说明差距是 1 个死地址 vs 5 个里 4 个可用。~~
   **（2026-09-26 修正）** 密度已经不是问题（`/1` 实测 3.05/域名、100% 多地址），
   所以这一条不再成立。替换为：**提高地址正确性** —— 对每条地址判「TCP 可达 +
   证书覆盖原域名」，把不可用的排到后面或剔除。抽测 25 域名仅约 7 成可用，这是
   当前真正卡住救援率的量。
2. **规则支持「拨号名」而不只是 IP**。既然 `*.akamaihd.net` 族可用 edgesuite，
   规则就该能表达「这个域名去 dial 这个 edgesuite 名」，而不是只给一个 IP。
3. **运行时重解析**。S302 的 `dynamic a <name> 443` 会定期重查；watt 的 hosts 源是启动快照，长跑会过期。
4. **健康判据多维化**。目前只有连得上/连不上；可加延迟与状态码。

## 6. 一句话总结

S302 用**解密**换来了「换 SNI / 换 Host / 换 UA」的自由，代价是 Root、自签根证书、可被远端投毒的规则源。
watt 用**不解密**换来了免 Root 与端到端加密，代价是**只能换地址**。

两者面对同一个网络问题，S302 的解法更有效但更重；watt 的解法更轻但**强烈依赖规则质量** ——
~~而当前的 hosts 源平均只给 1.03 个地址，这正是我们此前 `PROXY_FAILED` 的真正原因。~~

**（2026-09-26 修正）** 上文那句「平均只给 1.03 个地址」已对 `/1` 实测推翻：
5225 域名 / 15952 地址 / 3.05 每域名 / 100% 多地址。今天 `PROXY_FAILED` 的
真正原因不是地址**数量**不够，而是地址**正确性**不够：抽测 25 个域名，约 7 成
可用（18/25 = 72%，独立复核 17/25 = 68%），约 3 成一个能用的地址都没有，失败
分为证书不匹配（架构上无解）、连接被拒、超时三类。**排序只能重排已存在的
地址，不能把错地址变成对的。**
