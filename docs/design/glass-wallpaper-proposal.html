卡片玻璃 + 自定义壁纸 · 方案

响应三件事：① 能上玻璃的卡片都上；② 支持自定义背景壁纸，设置放在设置页的「外观」组里和主题设置在一起； ③ 其它页面也一起准备。下面先给结论，再给逐卡清单、壁纸设计、其它页面的样子、降级风险和改动顺序。 视觉方向沿用你已经选定的 B 玻璃通透，参考实现是 io.github.kyant0:backdrop。

一句话结论

  • 卡片：把 DetourSectionCard 一处从 Filled 翻成 Glass，设置页 4 个分组 + 首页「规则状态」「命中规则」共 6 张卡一次性玻璃化；再补 6 个独立 DetourCard 调用点。密集文本列表（日志行、规则地址行）保持不透明，可读性优先。
  • 壁纸：新增一个「背景壁纸」设置，位于设置页「外观」组内、紧挨「磨砂玻璃」之后。内置 5 个程序绘制的渐变预设（零图片资源），也可选自己的照片；照片走系统相册选择器，不需要任何运行时权限。
  • 结构：真正的背景模糊必须能采样「身后」的像素，而现在 Scaffold 把内容垫在了底栏之上，没有任何东西从悬浮底栏下面经过，也没有壁纸层。所以要引入一层背景/壁纸层并让内容从底栏下穿过——这是本方案唯一的结构性决定。
  • 代价：引入 backdrop 依赖，推翻了 LiquidGlass.kt 注释里「不引入该依赖」的既有决定；库自身文档记录了一个 RenderThread SIGSEGV 风险，方案里给了分级门控与回退。

2 · 背景壁纸功能设计 本方案的核心

壁纸不只是「换个背景」——它是玻璃的采样源。没有壁纸，玻璃只能折射一片纯色，看起来就是「半透明白卡」； 有了壁纸，玻璃才真的在折射东西。壁纸 + 玻璃是配套的，这也是为什么壁纸设置要和「磨砂玻璃」放在同一组。

2.1 设置放在哪里

位置：设置页 → 「外观」组 → 紧挨「磨砂玻璃」之后、「字号」之前。这样从「取色 → 深色 → 主题色 → 圆角 → 磨砂玻璃 → 背景壁纸」是一条完整的外观动线， 用户调完玻璃顺手就能给它配一张底。

2.2 两个来源

(a) 内置预设（默认方案，零图片资源）：5 个程序绘制的渐变——品牌紫极光、冷蓝晨雾、暖砂、青苔、深色夜行。 它们不是位图，而是 Compose 的 Brush，不占安装包体积、任意分辨率不糊、深色模式下可切换。选预设时玻璃立刻有东西可折射，用户完全不需要碰文件选择器。

(b) 自己的照片：用 ActivityResultContracts.PickVisualMedia（Android 13+ 的系统相册选择器，旧版本走 ACTION_OPEN_DOCUMENT）。 它不需要 READ_MEDIA_IMAGES、不需要 READ_EXTERNAL_STORAGE——用户只授权那一张图，且授权是一次性的。 这正是这个「刻意只声明 5 个权限」的项目该选的方案：AndroidManifest.xml 里一个媒体/存储权限都不用加。

2.3 存到哪里

存 filesDir，不存 content:// URI。相册选择器给的是一次性授权的 URI，进程重启或设备重启后就失效， 直接存 URI 会导致「今天设了壁纸，明天开机变成白底」。做法与仓库里已有的规则缓存一致：

  • 把选中的图片复制成 filesDir/wallpaper；
  • 再写一个小的 sidecar（如 filesDir/wallpaper.fmt）记录原格式 / 宽高，用于解码和失效判断；
  • Prefs 里只存 路径 + 版本号（版本号用来在换图时让 Compose 重新读取，避免图片缓存不刷新）。

仓库先例：core/RulesRepository.kt 就是 filesDir/rules.json + filesDir/rules.json.source 的「主文件 + sidecar」写法（见该文件 :136、:147、:496、:499），壁纸沿用同一套，不引入新范式。

2.4 怎么渲染（层次图）

从底到顶一共五层。玻璃必须能采样到它下面的东西，所以壁纸层要画在同一个 backdrop 源里，而不是画在内容里。

⑤
内容 + 玻璃卡片 / 底部导航栏 —— 最顶层。玻璃在这里用 drawBackdrop 采样它下面 ①–④ 的合成结果。
④
遮罩 scrim —— 一层半透明白（浅色模式）或深（深色模式），浓度用户可调。它才是「照片上文字还能看清」的保证，且必须随深浅色模式切换。
③
用户照片（如果设了）—— 已降采样到屏幕尺寸，ContentScale.Crop 铺满。未设则跳过。
②
柔和光斑 —— 2–3 个径向渐变，给玻璃提供明暗变化，否则纯渐变底上玻璃看不出来。
①
品牌渐变底 —— 永远存在，是「无壁纸」时的默认背景，也是照片加载失败时的兜底。
为什么必须有遮罩：用户可能选一张很花、很亮的照片（比如白天的海边）。没有遮罩，卡片上的深色文字会淹没在照片里。 遮罩把照片整体压向一个中性亮度，玻璃再在其上做模糊与提亮。遮罩浓度做成滑块，是因为「照片要好看」和「字要看得清」是一对矛盾， 只有用户自己知道偏哪边——给一个默认值（58%），把选择权留给他。

2.5 解码：必须降采样

相册里一张 4000×3000 的 JPEG，全分辨率解码约 48 MB（4 字节/像素）。这台模拟器只有 2 核 + 低内存标志， 直接 BitmapFactory.decodeFile 全图是实打实的 OOM 风险。 做法：先用 inJustDecodeBounds 读尺寸，按屏幕宽高算 inSampleSize，再解码到屏幕尺寸的 1–2 倍。 一张 4000×3000 降到约 1080×810，解码内存从 ~48 MB 降到 ~3.5 MB。

2.6 和四档玻璃的关系

磨砂玻璃档位壁纸 = 无壁纸 = 预设 / 照片
关闭 off 今天的观感：实底卡 + 纯色背景。完全不变。 卡片必须够不透明（建议 α≈0.93）才能压在照片上读；此时壁纸只作背景装饰，不参与折射。
低 low 半透明 + 轻微模糊（blurRadius = 8.dp 终于生效）。 推荐默认组合。玻璃开始真的折射壁纸，性能开销可控。
高 high 更明显的模糊（16.dp）+ 更强高光。 最佳观感，也是壁纸 + 玻璃最想达到的效果。
自动 auto 按设备决定：低端机 → off，其它 → high。注意这台模拟器会解析成 off，所以验证时必须手动把「磨砂玻璃」设成「高」。

四档本身不需要改形状。resolveDetourGlass 的注释已经写明：blurRadius 一直是占位符， 「保留这一档是为了真模糊落地时设置不必改形」。现在真模糊来了，blurRadius（8dp / 16dp）直接接上即可。

4 · 降级与风险 每一档都要能渲染，不能白屏

这个项目把「崩溃」当一等问题。所以玻璃与壁纸都必须有逐级回退：低版本走今天的实底，库出问题走今天的 liquidGlass。 下面每一行都有对应的兜底，没有哪一档会白屏。

情形能力回退 / 处理
API < 31
Android 11 及以下		 无 RenderEffect，backdrop 的模糊无法工作 整条 backdrop 路径不启用，退回今天的 Modifier.liquidGlass（半透明 tint + 高光边框）。卡片必须正常渲染为「磨砂白卡」，绝不能变透明或空白。壁纸仍可用（它只是绘制，不依赖 API 31）。
API 31–32
Android 12 / 12L		 可模糊，lens（RuntimeShader）不可用 启用 blur，不启用 lens。lens 需要 CornerBasedShape，低版本上直接跳过该效果。
API ≥ 33
Android 13+		 全部可用：颜色滤镜 → 模糊 → lens 完整效果。效果顺序必须是「颜色滤镜 → 模糊 → lens」，顺序错了会得到错误的折射。
SIGSEGV in RenderThread
库 FAQ 记录的原生崩溃		 库已知风险 三重缓解：① 门控在玻璃档位之后——off 档根本不走 backdrop 路径；② 保留今天的 liquidGlass 作为可回退实现，出问题一个开关切回；③ 必须在真机上验证（模拟器的 RenderThread 行为不代表真机），确认无崩溃才允许默认开启。
本机 auto 解析为 off — isLowEndDevice 在这台模拟器（2 核 + 低内存标志）恒为 true，auto → off。任何设备验证都必须先把「磨砂玻璃」显式设为「高」，否则看到的是回退路径，会误判成「玻璃没实现」。
照片过大 OOM 风险 强制 inSampleSize 降采样（见 2.5）；解码失败时回退到品牌渐变底，并给一条提示。
照片是浅色 / 高对比 文字可读性 遮罩层保证最低对比度；玻璃 = 关闭时卡片不透明度提到 α≈0.93。

5 · 实施顺序与改动文件 按此顺序落地，每步可独立验证

  1. 加依赖。 android/app/build.gradle.kts 加入 io.github.kyant0:backdrop:2.0.1（Apache-2.0，minSdk 21，jvmTarget JVM_11，会带入 io.github.kyant0:shapes:1.2.1）。仓库已是 google() + mavenCentral()，无需改仓库。本仓库无 libs.versions.toml，依赖按现有风格写成字面量字符串。
  2. 重写玻璃修饰符。 ui/components/LiquidGlass.kt 把 Modifier.liquidGlass 升级为「backdrop 可用时走真模糊，否则走今天的 tint 路径」，并重写它的 KDoc——现有注释明确写着「不引入该依赖」，这句话必须被替换成新的取舍说明，不能留着自相矛盾。
  3. 一处翻卡。 ui/components/DetourListItem.kt DetourSectionCard 的 style = DetourCardStyle.Filled 改为 Glass。这一步同时覆盖设置页 4 组与首页 2 张卡，是观感变化最大的一步，建议先单独截图确认。
  4. 补独立卡片。 HomeScreen.kt（:493、:598、:630）与 RulesScreen.kt（:461）改为 Glass。不动 HomeScreen.kt:570 的 ModeRow（弹窗内）与 LogsScreen.kt:287 的 LogRow（密集文本），理由见第 1 节。
  5. 接线 blurRadius。 ui/theme/Tokens.kt 让 resolveDetourGlass 的 blurRadius（low = 8.dp / high = 16.dp）真正传给 backdrop 的 blur(...)。四档字符串不动，设置不必改形。
  6. 背景层 + backdrop 源。 MainActivity.kt 在 DetourAppBody() 里：① 引入 rememberLayerBackdrop { drawRect(背景); drawContent() }；② 在 Surface 之下、内容之上插入 ①–④ 五层背景（见 2.4）；③ 把底部导航栏改为 Modifier.drawBackdrop(...)。这是本方案唯一的结构性改动。
  7. 让内容从底栏下穿过。 MainActivity.kt 去掉 Scaffold 对内容的 insets 底部内边距，改由每个屏幕自己用 contentPadding 留出底栏高度。这一步不做，玻璃底栏就只能折射纯色，看不出任何效果——这是「底栏玻璃有没有意义」的关键。
  8. 壁纸数据层。 core/Prefs.kt 新增 wallpaper（预设名 / 照片路径）与 wallpaper_version、wallpaper_scrim 三个键，配套 updateXxx；照片复制进 filesDir 的写入逻辑参照 core/RulesRepository.kt 的「主文件 + sidecar」写法。
  9. 设置页新行。 ui/SettingsScreen.kt 在 SettingsSection.APPEARANCE 里、「磨砂玻璃」之后插入「背景壁纸」行（SettingsScreen.kt:419 那一段的下面），并接 PickVisualMedia 启动器。ActivityResultContracts 本文件已 import，直接用。

一个必须说清、否则会被误解的点：现有的「跟随壁纸取色」（settings_dynamic_color）和「主题色 → 动态」（settings_theme_color_dynamic） 里的「壁纸」，指的是 Android 系统壁纸给 Material You 提供调色板，和本方案要加的「应用内背景壁纸」是两回事。 前者决定 App 用什么颜色，后者决定 App 背后长什么样。两行文案必须写清楚差别，否则用户会以为「壁纸功能早就有了」。
需要你拍板的三个判断： ① 日志页要不要玻璃？本方案建议不要（密集文本），但若你想要「每条日志一张卡」的观感，可以推翻； ② 预设数量与配色，本方案给了 5 个，可增减； ③ 遮罩默认 58%，是「照片好看」与「字看得清」的折中，你更偏哪边可以直接说。
