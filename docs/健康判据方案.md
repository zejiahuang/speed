# 健康判据方案：延迟 + 会话层观测

> 起因：上游 hosts 源曾被认为平均每域名只有 1.03 个地址，而 S302 靠多 IP + 熔断 +
> `unhealthy_latency` / `unhealthy_status` 做优选。watt 要对齐，但有一个
> **硬约束必须先说清**。
>
> **修正（2026-09-26 对 `https://abhuang.dpdns.org/1` 实测）**：那个 1.03 的
> 密度结论已经不成立。同一端点今天给出 **5225 域名 / 15952 地址 / 平均 3.05
> 地址每域名 / 100% 的域名都有多于一个地址**（旧记录：2879 / ~2900 / 1.03 /
> 79 个，2.7%）。所以本文「低密度」这个前提只在**地址被削到只剩一个**时才
> 成立，不能再用它描述整份规则源。真正的瓶颈已从**地址数量**移到**地址正确
> 性**：抽测 25 个域名、对每条规则地址做 TCP 可达 + TLS 证书校验
> （`server_hostname` = 该域名），**约 7 成可用**（team-lead 测得 18/25 = 72%，
> 我复核另抽 25 个得 17/25 = 68% —— 比例会随样本与时刻波动，量级稳定在
> 七成上下），即约 3 成的域名**一个能用的地址都没有**。失败分成三类且不可
> 混为一谈——证书不匹配（连得上但证书不覆盖该域名）、连接被拒
> （refused/reset/EOF）、超时。证书不匹配在**不 MITM** 的前提下架构上无解，
> 唯一出路是换一个正确的地址。**排序只能重排已存在的地址，不能把错地址变成
> 对的**——这正是本文后面的判据仍然有价值的地方。
>
> 复现：拉 `/1`，随机抽 25 个域名，对每条的地址 `connect(ip,443)` +
> `ssl.wrap_socket(server_hostname=domain)`，统计成功域名比例。

## 0. 先说不能做的那件事

**「状态码」在内核侧不可见。**

这不是没实现，是不解密的必然结果。watt 转发的是加密字节，HTTP 状态码在 TLS 记录里，
内核看不到。TUN 路径同理。所以：

```text
S302  能看状态码 → 因为它在本机终结 TLS
watt  看不到     → 因为端到端加密是设计前提
```

**只有客户端能提供状态码。** 于是有三条路：

| 方案 | 代价 | 判断 |
|---|---|---|
| 让客户端回报状态码 | 需要客户端配合 + 一个本地 IPC 接口 | 可行但侵入，且只对自家客户端有效 |
| **用会话层观测量替代** | 零侵入，不需要解密 | **推荐** |
| 放弃状态码判据 | 少了最强信号 | 备选 |

下面走第二条。

## 1. 现状盘点：已有的比想象中多

`watt-rules/src/selector.rs` 已经实现了 S302 那套的骨架：

| S302 的配置 | watt 的对应物 | 状态 |
|---|---|---|
| `fail_duration 3s` | `IpSelectorConfig.failure_cooldown`（60s） | ✅ 已有 |
| `max_fails 3` | `IpStat.consecutive_failures` | ✅ 已有 |
| `unhealthy_latency 500ms` | `IpStat.ewma_rtt_ms` + `ewma_alpha` | ✅ 已有 |
| `lb_policy random_choose N` | `rank()` 稳定排序 + 文档顺序 | ✅ 已有（确定性版本） |
| `unhealthy_status 5xx` | —— | ❌ **看不到状态码** |
| `dynamic a <name>` | **已实现**（tick 级重解析，见第 7 节） | ✅ 已有 |

排序键已经是四段：冷却 → RTT → 连续失败 → 文档顺序。**所以「加延迟」这件事基本已经做完了**，
真正缺的是「一个不需要状态码的、能区分『连上了但没服务』的信号」。

## 2. 核心提案：会话层观测

内核虽然看不到内容，但**看得到形状**。一条上游连接结束后，这些量全部可得：

| 观测量 | 含义 | 采集点 |
|---|---|---|
| 上行字节数 | 客户端发了多少 | `copy_bidirectional` |
| **下行字节数** | 上游回了多少 | `copy_bidirectional` |
| **首字节时间** | 从 CONNECT 成功到上游第一个字节 | `copy_bidirectional` |
| 连接时长 | 存活多久 | `copy_bidirectional` |
| 是否被 RST | 对端是否强拆 | 读写错误类型 |

### 判据

```text
连接失败                        → Refused   （已有，走 report_failure）
连接成功 + 下行字节 > 0          → Healthy   （服务在响应）
连接成功 + 下行字节 == 0 + 对端关闭 → Silent   （连上了但没有任何数据回来）
```

**`Silent` 就是状态码的替代品**，它抓住的是「TCP 通了但这条流被黑洞了」：

- SNI 被中间盒阻断（握手完成后被静默丢弃）
- 服务端接受连接后立刻挂断
- 上游被防火墙吞掉后续报文

### ⚠️ 实测纠正：证书不匹配**不在**这一类里

我最初把「证书不匹配导致客户端中止」也列进了 `Silent`。**实测证明这是错的。**

对真实 Akamai 边缘测出的字节计数：

```text
proxy: SESSION store.steampowered.com -> 23.33.126.177 up=469 down=3105
```

`down=3105` 是 ServerHello + **证书**。也就是说：**服务器先把证书发下来，客户端才拒绝它。**
字节双向都流了，会话以 `Healthy` 结束。

**内核看不出这次拒绝**，因为要看出它，就必须知道那些字节是什么意思——而这正是「不终结 TLS」所放弃的东西。
这条限制没有绕法，不要试图用启发式（比如「会话太短」「上行字节太少」）去猜：
那会把正常的短响应也判成坏地址。

所以准确的表述是：

| 失败类型 | 内核能否察觉 | 靠什么 |
|---|---|---|
| 连接建不起来 | **能** | `Refused` |
| TCP 通了但零响应 | **能** | `Silent` |
| 证书不匹配、客户端拒绝 | **不能** | —— |

第三类只有客户端知道。若要利用它，只能由客户端回报（需要 IPC 与客户端配合），
而不是在内核里猜。

### 为什么 `Silent` 仍然值得做

它把「连得上」和「连得上且有服务」分开了。旧判据下，一个黑洞地址会被记成成功，
于是选择器永远学不到它有问题，每次都先试它、每次都白等一个超时。
`Silent` 让这种地址沉下去。

### 为什么这比状态码更合适

状态码是**应用层**的，它告诉你「这个 URL 返回 404」——那是正常的业务结果，
不该让内核降低这个地址的健康度。而 `Silent` 是**传输层**的，它说的是
「这条路通不了」——那才是内核该学的东西。

**内核不该用应用层语义判断传输层健康。** 看不到状态码反而避免了误判。

## 3. 单候选域名的处理（地址被削到一个时才成立）

**前提修正**：本节原来假设「平均 1.03 个地址 / 大多数域名只有一个候选」，这是
对旧规则源的判断。2026-09-26 对 `/1` 实测为 5225 域名 / 15952 地址 / 3.05 每
域名，**100% 的域名都有多于一个地址**，选择器有真实排序空间。所以下面这条只
适用于**被削到单候选**的域名——例如其余地址都被判为拒绝或超时之后，或操作者
只给了一个地址。

对这类域名，健康判据的价值**不是排序，而是快速失败 + 缓存结论**：

```text
第一次请求：规则地址超时 → 回退系统解析 → 成功
            ↓ 记下「这个规则地址是坏的」
第二次请求：直接跳过规则地址，先试系统解析
            ↓ 省掉一次 CONNECT_TIMEOUT
N 分钟后：  坏地址结论过期（地址可能恢复），重新试规则地址
```

现状：`proxy.rs` 已经做到了「回退」，但**每次都要重新付一次超时代价**。
这就是要补的部分。

### 需要的东西

1. **坏地址结论要能查到**：`IpStat` 已经按地址索引了，`in_cooldown()` 就是现成的。
   `rank()` 把冷却中的地址沉底——单候选时沉底等于「还是它」，所以需要调用方
   显式判断「唯一候选在冷却中 → 直接跳过」。
2. **TTL**：`failure_cooldown` 默认 60 秒，对「地址真的挂了」太短。
   建议对**单候选**场景用更长的冷却（比如 10 分钟），因为此时试错的收益为零、代价是一次超时。
3. **`Silent` 也要计入**：目前只有 connect 失败才 `report_failure`。
   `Silent` 应该也降权，但要**比 Refused 轻**——毕竟 TCP 是通的。

## 4. 建议的接口改动

```rust
/// 一条上游连接结束后的观测结果。
pub enum Outcome {
    /// 连接失败，对端没接受。
    Refused,
    /// 连接成功，有数据回流。
    Healthy { first_byte: Duration },
    /// 连接成功，但一个字节都没回来就关了。
    Silent,
}

impl IpSelector {
    /// 记录一次会话结果。`Refused` 走现有的 report_failure。
    pub fn report_outcome(&mut self, addr: IpAddr, outcome: Outcome, now: Instant);
}

impl IpStat {
    /// 静默次数。与 `consecutive_failures` 分开计，因为含义不同：
    /// 一个是「路不通」，一个是「路通但没人应答」。
    pub silent: u32;
}
```

排序键加一段：**冷却 → 静默 → RTT → 连续失败 → 文档顺序**。
静默排在 RTT 之前，因为「没人应答」比「慢」严重得多。

调用点：`proxy.rs` 的 `copy_bidirectional` 收尾处。它已经知道两个方向的字节数了。

## 5. 不做的事（以及为什么）

| 不做 | 理由 |
|---|---|
| 主动健康探测（后台 ping 所有规则地址） | 域名数 × N 个地址（`/1` 2026-09-26 实测为 5225 × 平均 3.05），会变成一台扫描器；且探测结果与真实请求不等价——尤其是证书不匹配这类「TCP 通、TLS 不认」的失败，ping 判不出来 |
| 客户端回报状态码 | 需要 IPC + 客户端配合，且内核本不该用应用层语义判断传输层健康 |
| 云端共享健康数据 | 延迟和可达性是**按网络**的，别人测出来的结果对你无意义 |
| 用状态码做熔断 | 看不到；且 4xx 是正常业务结果，不该降权 |

---

## 6. 落地顺序

1. **`Outcome` + `report_outcome` + `IpStat.silent`**（纯逻辑，可单测，无 I/O）
2. **`proxy.rs` 在 `copy_bidirectional` 收尾时上报**（一处改动）
3. **被削到单候选的域名跳过冷却中的地址**（`proxy.rs` 里显式判断。注意
   `/1` 2026-09-26 实测每个域名都有多于一个地址，所以这一步是兜底而非主路径）
4. **`Silent` 的权重与冷却时长调参**（先用保守默认值，跑对比再定）

第 1 步不依赖任何网络，先做完再谈调参。

## 7. 运行时重解析（对齐 S302 的 `dynamic a <name>`）

### 7.1 为什么不能每请求解析

拨号名最初的实现是**每个请求现解析**。这有两个问题：

1. **浪费**：为了知道一件几分钟才变一次的事，付一次 DNS 查询/请求。
2. **致命**：**引擎用不了**。TUN 的数据面不能阻塞，而解析会阻塞——所以引擎此前
   **完全忽略拨号名**，这个功能在最需要它的平台上等于不存在。

### 7.2 做法：tick 级重解析 + 缓存

在 `Router` 上放一个缓存，键是**条目 key**，值是解析出来的地址：

```rust
resolved_dial: HashMap<u32, Vec<IpAddr>>

pub fn resolve_dial_names<F>(&mut self, resolve: F) -> usize
where F: FnMut(&str) -> Vec<IpAddr>
```

- `plan()` 把缓存里的地址**接在字面地址之后**（字面是作者已声明的偏好，名字是可能过期的查询）。
- 解析器由调用方提供——这一层是纯的，不碰 I/O，所以能脱离网络单测。
- **`replace_rules` 必须清空缓存**：条目 key 是规则集里的下标，换了规则集之后旧 key
  会指向毫不相干的条目。

### 7.3 谁来驱动

| 消费方 | 驱动者 | 原因 |
|---|---|---|
| CONNECT 代理 | `proxy::serve` 起的后台线程，60 秒一轮，**启动时先跑一次** | 启动不跑的话，第一个 tick 之前拨号名是死的，读起来像「功能不工作」 |
| TUN 引擎 | 守护进程的 `--tick` 循环 | 引擎自己不能解析：会阻塞数据面 |

引擎接上之后，`plan.addresses` 里就自然带上了名字解析出的地址——
**数据面一行没改**。

### 7.4 一个被删掉的中间态

代理里原本有 `Stage::Dial`（每请求解析）和 `Stage::Literal`（字面地址）两段。
缓存化之后，名字的地址从 `addresses` 进来，`Stage::Dial` 会解析出**同样的**地址
然后被去重掉——变成死代码。已删除，现在是两段：

```text
规则地址（字面 + 已解析的名字）→ 系统解析 → 502
```

### 7.5 还没做的

**缓存没有 TTL。** 现在只在 tick 上整体重算，所以一次失败的解析要等到下一轮才有机会
恢复，而一条已经解析成功的名字在下一轮之前不会失效。对分钟级的变化够了，
但如果要更细的控制（比如按名字记 TTL），得把 `HashMap<u32, Vec<IpAddr>>` 换成带时间戳的结构。
